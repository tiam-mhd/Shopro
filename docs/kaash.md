# قابلیت «کاش»

## خلاصهٔ معماری پیش از پیاده‌سازی

- workspace فعلی monorepo با React 19، TypeScript، Vite، React Router و TanStack Query در `apps/web`، NestJS و REST زیر `/api/v1` در `apps/api`، قراردادهای مشترک در `packages/contracts` و Prisma/PostgreSQL است.
- مسیرهای عملیاتی زیر `/app` در `App.tsx` داخل `BusinessGate` و پوستهٔ مشترک رندر می‌شوند؛ انتخاب کسب‌وکار/شعبه پیش از عملیات همگام و از عضویت سروری تأیید می‌شود. فهرست واقعی مسیرها شامل داشبورد، onboarding، اشتراک، ویترین، فروش، فاکتورها و جزئیاتشان، مشتریان/تأمین‌کنندگان، کالا/خدمت و دسته‌ها، موجودی و شمارش انبار، خرید، هزینه و دسته‌ها، امور مالی، دفتر، گزارش و تنظیمات است.
- صفحه‌های عمومی ویترین، ورود و پنل مدیریت بیرون از پوستهٔ عملیاتی‌اند. پنل فعلی `/system-admin` با نشست کوکی مستقل و guard سرور برای حساب تک‌مالک `shopro_super_admin` اداره می‌شود؛ بخش «کاش‌ها» در همین ناوبری قرار می‌گیرد.
- فرم‌ها و modalهای عملیاتی از `components/Modal.tsx` و لایه‌های backdrop مشترک استفاده می‌کنند؛ launcher به شکل یک portal سراسری روی این overlayها قرار می‌گیرد تا فرم زیرین بسته یا بازنشانی نشود. focus و inert بودن محتوای زیرین هنگام بازبودن کاش مدیریت می‌شود.
- Service worker با Workbox درخواست‌های `/api/` را وارد cache نمی‌کند. صف آفلاین موجود مختص فروش است و برای متن حساس کاش مناسب نیست؛ این قابلیت در نبود شبکه ارسال را متوقف می‌کند و draft را تا retry در حافظهٔ همان نشست نگه می‌دارد.

## ثبت پیشنهاد و رفتار شبکه

- launcher فقط در پوستهٔ عملیاتی `/app` و پس از تأیید عضویت/شعبه نمایش داده می‌شود. مسیر ورود، صفحات عمومی ویترین، پنل مدیریت و خود صفحه‌های پیشنهاد از آن جدا هستند. یک portal در modal جاری قرار می‌گیرد تا همان یک دکمه در modalهای تو‌در‌تو هم قابل دسترسی بماند.
- فرم فقط یک textarea و «ثبت کاش» دارد. متن با newline و emoji حفظ می‌شود؛ فضای ابتدا/انتها حذف و CRLF به LF تبدیل می‌شود. سقف سرور ۱۰۰۰ code point است.
- ارسال `POST /api/v1/kaash` نیازمند نشست کاربر و CSRF است. سرور عضویت فعال و شعبهٔ انتخاب‌شده را از نشست/هدرهای scope تأییدشده می‌گیرد؛ شناسه‌های مالکیت در بدنه پذیرفته نمی‌شوند.
- کلید یکتای UUID هر retry در `clientSubmissionId` می‌ماند. کلید advisory تراکنشی PostgreSQL و unique `(user_id, client_submission_id)` چند retry/تب همزمان را یکی می‌کنند؛ متن یکسانِ همان کاربر در همان شعبه طی ۳۰ ثانیه نیز به همان ردیف وصل می‌شود. محدودیت ضداسپم ۱۵ پیشنهاد برای هر کاربر در ۲۴ ساعت است.
- هیچ صف آفلاین عمومی برای متن وجود ندارد. بدون اینترنت دکمه غیرفعال و متن در حافظهٔ همین نشست باقی می‌ماند؛ پس از اتصال، کاربر دستی retry می‌کند. متن به localStorage، IndexedDB، cache سرویس‌ورکر یا analytics فرستاده نمی‌شود و فقط پس از پاسخ موفق پاک می‌شود. بارگذاری دوبارهٔ صفحه draft حافظه‌ای را پاک می‌کند.

## API و دسترسی مدیریت

- `POST /api/v1/kaash`: کاربر واردشده، CSRF، membership فعال و شعبهٔ مجاز.
- `GET /api/v1/system-admin/kaash/counts`, `POST .../query`, `GET .../:id`, `PATCH .../:id`, `GET .../:id/story`: فقط guard نشست مستقل super_admin فعلی و CSRF برای تغییرات.
- جست‌وجو، فیلتر status/module/date و صفحه‌بندی در بدنهٔ POST و سمت سرور انجام می‌شوند. فهرست فقط پیش‌نمایش محدود متن و تلفن پوشیده برمی‌گرداند. متن کامل، مشخصات محدود کاربر/کسب‌وکار و یادداشت داخلی فقط در جزئیات پنل مالک است.
- چرخهٔ وضعیت: `NEW → REVIEWING → PLANNED → IN_PROGRESS → RELEASED`؛ آرشیو از وضعیت‌های کاری مجاز است و مورد بایگانی‌شده فقط به بررسی برمی‌گردد. سرور هر پرش خارج از این چرخه را رد می‌کند.
- `kaash_submissions` متن/مالکیت/scope/مبدأ/status و کلید ارسال را نگه می‌دارد؛ `kaash_submission_events` تاریخچهٔ وضعیت و یادداشت داخلی را ثبت می‌کند. رویداد audit عمومی فقط مبدأ و scope لازم را دارد و متن پیشنهاد را ذخیره نمی‌کند.

## صفحهٔ جزئیات و استوری

- بخش «کاش‌ها» به ناوبری تک‌مالک فعلی اضافه شده است. فهرست صفحه‌بندی‌شده، جست‌وجو، فیلترها، جزئیات، کنترل چرخه، یادداشت داخلی، تاریخچه و کپی شناسه را دارد.
- نمای استوری از endpoint جداگانه‌ای می‌خواند که فقط متن و تاریخ را برمی‌گرداند. نام، تلفن، کاربر، کسب‌وکار/شعبه، مبدأ، شناسه و یادداشت داخلی به این view نمی‌رسند. متن بلند به چند قاب ۹:۱۶ تقسیم می‌شود و اتصال متن قاب‌ها دقیقاً متن اصلی است.
- preview نسبت ۹:۱۶ دارد؛ در viewport برابر ۱۰۸۰×۱۹۲۰ و حالت «آمادهٔ تصویر» قاب دقیقاً ۱۰۸۰×۱۹۲۰ CSS px است. چاپ/ذخیرهٔ مرورگر نیز همین اندازه را هدف می‌گیرد؛ تولید PNG داخل برنامه یا dependency/سرویس تصویر اضافه نشده است.
- رفرنس‌های کاربر در `0-DOCS/Images/Kash-dark.png` و `Kash-light.png` حفظ شده‌اند؛ نسخه‌های بهینهٔ محلی برای رابط در `apps/web/public/icons/kaash-dark.webp` و `kaash-light.webp` هستند. هر دو تم، فونت Vazirmatn و لوگوی واقعی مخزن را استفاده می‌کنند.

## داده‌پایگاه، migration و بازگشت

- migration افزایشی `prisma/migrations/20261111110000_kaash_feedback/migration.sql` جدول‌ها، enumها، قید طول، foreign keyها و indexهای کاربر/کسب‌وکار/status/module/تاریخچه را اضافه می‌کند و دادهٔ موجود را تغییر نمی‌دهد.
- استقرار همان فرمان‌های repo است: `npm run db:generate` و سپس `npm run db:deploy`. متغیر تازه‌ای لازم نیست؛ اتصال دیتابیس از `DATABASE_URL` موجود خوانده می‌شود.
- بازگشت کد به نسخهٔ قبل، جدول‌ها و داده‌های افزوده را دست‌نخورده می‌گذارد. migration مخربِ down عمداً ساخته نشده تا متن خصوصی حذف نشود؛ بازیابی پایگاه از مسیر backup/restore موجود در `docs/backup-restore.md` است. حذف نهایی این داده‌ها باید پس از تصمیم نگه‌داری و backup مالک انجام شود.

## راستی‌آزمایی انجام‌شده

- API typecheck و ۱۱۳ تست API، web typecheck و ۲۲ تست web، Prisma generate و build وب موفق شدند.
- migrationها روی PostgreSQL موقت محلی اعمال و دوباره اجرا شدند؛ اجرای دوم migration معوقی نداشت. آزمون HTTP یکپارچهٔ احراز هویت و scope، جریان ثبت کاش، idempotency و دسترسی مالک را هم اجرا کرد.
- smoke مرورگر Edge با API ساختگی، مسیر modal کاربر و حفظ modal زیرین، فهرست/جزئیات پنل و استوری را در viewport دسکتاپ، موبایل ۳۹۰×۸۴۴ و استوری ۱۰۸۰×۱۹۲۰ بررسی کرد. قاب PNG مرورگر دقیقاً ۱۰۸۰×۱۹۲۰ بود؛ تصویر خروجی موقت بود و در مخزن نگه‌داری نمی‌شود.
- `git diff --check` موفق بود. هیچ deploy، migration محیط واقعی، push یا تغییر تنظیمات Runflare انجام نشد.
