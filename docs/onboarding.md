# راه‌اندازی اولیه در شاپرو

## مسیرهای کاربر

- کاربر بدون کسب‌وکار پس از ورود با OTP فرم کوتاه ساخت کسب‌وکار و شعبهٔ اول را می‌بیند. نام کسب‌وکار و شعبه لازم‌اند؛ نوع فعالیت اختیاری است. زبان رابط فارسی، تاریخ‌های رابط شمسی با timezone کسب‌وکار و واحد نمایش پیش‌فرض تومان است. ساخت کسب‌وکار و شعبه و حساب‌های پایه در یک تراکنش انجام می‌شود.
- کاربری که از قبل عضو کسب‌وکار است مستقیم به `/app/onboarding` می‌رود. کسب‌وکار یا شعبه دوباره ساخته نمی‌شود؛ نام کسب‌وکار، شعبهٔ جاری و نقش از API عضویت و دسترسی شعبه می‌آیند.
- عضو جدیدی که مالک به حساب موجود اضافه کرده نیز از همان مسیر وارد می‌شود و با نقش و شعبهٔ مجازش راهنمای متناسب می‌بیند. در نسخهٔ فعلی دعوت توکنی یا endpoint جداگانهٔ پذیرش دعوت وجود ندارد؛ مالک عضویت را از تنظیمات ایجاد می‌کند و کاربر هنگام ورود عضو می‌شود.

## مراحل و محدودیت‌های محصول

چک‌لیست از کسب‌وکار، شعبه، اشتراک، انتخاب روش شروع مالی، کالاها، عملیات واقعی، مشاهدهٔ نتیجه و اعضا تشکیل می‌شود. انتخاب‌ها و ردکردن مرحله‌ها در API ذخیره می‌شوند؛ وجود کالا، سند ثبت‌شده و دسترسی شعبه از داده‌های واقعی محاسبه می‌شود. مالک و حسابدار می‌توانند روش شروع مالی را انتخاب کنند. نقش‌های مدیر، صندوقدار و مشاهده‌گر فقط اقدام‌های مجاز API را می‌بینند یا اجرا می‌کنند. هیچ مرحلهٔ اختیاری شرط ورود به برنامه نیست.

اشتراک از API فعلی هر شعبه خوانده می‌شود و صفحهٔ اشتراک فعلی شاپرو جزئیات مدت، مبلغ کل، معادل ماهانه و وضعیت تأیید پرداخت را نمایش می‌دهد. onboarding قیمت یا فعال‌سازی جداگانه‌ای پیاده نمی‌کند. در حالت `ENFORCE`، ثبت‌های عملیاتی تابع guard اشتراک هستند؛ پرداخت کارت‌به‌کارت فقط پس از تأیید سرور فعال می‌شود و وضعیت redirect یا مرورگر موفقیت پرداخت نیست. در حالت `OBSERVE` وضعیت واقعی نشان داده می‌شود اما مانع عملیات نیست. درگاه پرداخت production در حال حاضر متصل نیست.

دو روش شروع مالی ثبت می‌شوند. ورود یکپارچهٔ ماندهٔ صندوق و بانک، طلب‌ها و بدهی‌ها هنوز API ندارد؛ onboarding آن را صریحاً «فعلاً پشتیبانی نمی‌شود» نشان می‌دهد و آن مرحله تکمیل‌شده نمی‌شود. موجودی اولیهٔ کالا را می‌توان از شمارش واقعی انبار ثبت کرد. از سند آزمایشی یا ماندهٔ نامتوازن استفاده نمی‌شود.

فرم کالای کوتاه از API فعلی کالا و واحد استفاده می‌کند. قیمت فروش از بهای خرید پیش‌فرض و تعداد اولیه جداست. اعداد فارسی و عربی و مبالغ ریالی/تومانی با `BigInt` تبدیل می‌شوند؛ عملیات مالی تازه تا پاسخ سرور قطعی نشود انجام‌شده اعلام نمی‌شود. ساخت کالا و انتخاب‌های onboarding به اینترنت نیاز دارند. صف آفلاین موجود فقط فروش را پشتیبانی می‌کند و همین محدودیت در رابط روشن می‌ماند.

پیشنهاد نصب فقط وقتی `beforeinstallprompt` مرورگر در دسترس باشد و کاربر اولین عملیات را ثبت کرده و داشبورد را دیده باشد نمایش داده می‌شود. مرورگرهایی که prompt نصب ندارند پیام ساختگی نمی‌گیرند. راهنمای ورود، OTP موجود پروژه را به‌کار می‌برد.

## API و ذخیره‌سازی

- `POST /businesses` کلید `Idempotency-Key` اختیاری می‌پذیرد. wizard آن را در storage محلی نگه می‌دارد تا پاسخ مبهم را با همان درخواست تکرار کند. سمت سرور hash ورودی را به شناسهٔ کاربر و کلید متصل می‌کند؛ استفادهٔ دوباره از همان کلید با payload متفاوت رد می‌شود.
- `GET /onboarding` عضویت فعال، دسترسی شعبه، وضعیت اشتراک، کالاها، اسناد واقعی ثبت‌شده و وضعیت پیشرفت را با scope درخواست جاری می‌خواند.
- `PATCH /onboarding/progress` روش شروع مالی، ردکردن/ادامهٔ مرحله و مشاهدهٔ نتیجه را ثبت می‌کند.
- `POST /onboarding/events` فقط نام رویداد، نام مرحلهٔ allowlistشده و نوع کلی دستگاه می‌پذیرد. شناسه‌ها و نقش از نشست و scope سمت سرور به دست می‌آیند.
- جدول `onboarding_progress` انتخاب‌ها و مرحله‌های ردشده را در سطح کسب‌وکار/شعبه نگه می‌دارد. `onboarding_result_views` مشاهدهٔ نتیجه را برای همان کاربر و شعبه ثبت می‌کند تا فعال‌سازی کاربر دعوت‌شده از مشاهدهٔ شخص دیگر استنباط نشود. `onboarding_events` فقط دادهٔ کمینهٔ رویداد را نگه می‌دارد.

تمام endpointها نشست احراز هویت‌شده دارند. دسترسی کسب‌وکار و شعبه در server guard و membership بررسی می‌شود؛ انتخاب‌های UI مجوز ایجاد نمی‌کنند. رویدادها شامل نام مشتری، تلفن، شماره سند، مبلغ، محتوا، token یا user-agent خام نیستند. خطای ثبت رویداد در مرورگر جریان onboarding را متوقف نمی‌کند. تکمیل فعال‌سازی از سند ثبت‌شده و نشانگر مستقل مشاهدهٔ نتیجه محاسبه می‌شود، نه از وجود analytics.

رویداد `invite_accepted` در نسخهٔ فعلی ارسال نمی‌شود چون مدل فعلی، دعوت را به پذیرش جداگانه تبدیل نمی‌کند. برای اندازه‌گیری واقعی پذیرش، ابتدا باید چرخهٔ دعوت/پذیرش مستقل محصول اضافه شود.

## Migration و تست

Migration راه‌اندازی `20261104110000_onboarding_progress` جدول‌های درخواست ساخت تکرارپذیر، پیشرفت شعبه، مشاهدهٔ نتیجه و رویدادهای کمینه را اضافه می‌کند. مسیرهای ساخت کسب‌وکار، subscription guard و رویدادهای ثبت فروش/خرید/هزینه/صندوق/شمارش انبار به onboarding متصل شده‌اند.

برای اجرای یکپارچگی، `npm run test:integration:local` یک PostgreSQL تازه و محلی و موقت زیر `.tmp` می‌سازد و پس از اجرا پاک می‌کند؛ این فرمان نباید به پایگاه دادهٔ واقعی تنظیم شود. برای بررسی رابط ساخته‌شده از `npm run build` و `npm run test:e2e:browser-smoke` استفاده کنید. مرورگر iOS/Android و آزمون واقعی پذیرش دعوت در این مخزن وجود ندارد.
