# امنیت و عملیات پنل مدیریت شاپرو

## وضعیت و معماری

این پنل در monorepo فعلی ساخته شده است: React/Vite رابط را ارائه می‌کند و NestJS API آن را از همان origin میزبانی می‌کند. هر دو در image موجود Docker اجرا می‌شوند و Prisma به PostgreSQL فعلی متصل است. سرویس یا پایگاه‌دادهٔ دوم لازم نیست. route مدیریتی در UI دروازه دارد، اما کنترل دسترسی اصلی در API و نشست server-side اعمال می‌شود.

حساب مدیر محصول شاپرو از جدول `system_admins` می‌آید و با `users` و عضویت فروشندگان در کسب‌وکار تفاوت دارد. تنها نام کاربری پذیرفته‌شده `shopro_super_admin` است. OTP فروشنده و نشست فروشنده مستقل مانده‌اند؛ route ورود OTP برای مدیر حذف شده است. signup، دعوت، reset عمومی و endpoint ساخت مدیر در دسترس نیست.

Migration `20261111090000_admin_owner_panel` افزایشی است. داده‌های قبلی حفظ می‌شوند، کسب‌وکارهای موجود با `is_active=true` شروع می‌کنند و نشست‌های قدیمی مدیر باطل می‌شوند. اگر پیش از migration دقیقاً یک مدیر قدیمی وجود داشته باشد، همان شناسه به نام کاربری ثابت مالک متصل می‌شود تا مدیر دوم ساخته نشود. اگر چند ردیف مدیر قدیمی باشد، migration هیچ‌کدام را انتخاب نمی‌کند و startup متوقف می‌شود تا مالک با backup و بررسی پایگاه‌داده، وضعیت را حل کند. روی یک ردیف یگانهٔ قدیمی که هنوز password hash ندارد، Secret اولیه فقط اولین رمز آن ردیف را ثبت می‌کند؛ پس از ذخیرهٔ hash، deployهای بعدی رمز را تغییر نمی‌دهند.

## داده‌ها و بخش‌های عملیاتی

| موضوع | مدل یا منبع موجود | کاربرد و محدودیت |
|---|---|---|
| کاربران و کسب‌وکارها | `User`, `Business`, `BusinessMember` | جست‌وجوی نام/تلفن عضو و کسب‌وکار؛ مالک محصول به عضو فروشنده تبدیل نمی‌شود. |
| شعبه‌ها | `Branch`, `MemberBranch` | جست‌وجو و نمایش شعب فعال/غیرفعال و تعداد اعضا. |
| اشتراک | `SubscriptionPlan`, `SubscriptionPriceVersion`, `BranchSubscription`, `SubscriptionPeriod`, `SubscriptionOrder` | نمایش snapshot پلن، مبلغ، دوره و رویدادهای ثبت‌شده؛ قیمت‌های سفارش گذشته از تغییر قیمت آینده جدا هستند. |
| پرداخت و رسید اشتراک | `SubscriptionPaymentAttempt`, `SubscriptionManualPaymentSubmission` | صف رسید موجود با وضعیت‌های پروژه؛ تأیید و رد نیازمند دلیل و در API audit می‌شوند. رسید خصوصی فقط از route محافظت‌شده قابل دریافت است. |
| فروشگاه عمومی و سفارش | `Storefront`, `StorefrontOrder`, `StorefrontPaymentAttempt`, `StorefrontReceipt` | جست‌وجو و گزارش فقط‌خواندنی؛ workflow تغییر سفارش همچنان متعلق به فروشنده است. تلفن مشتری در پنل ماسک می‌شود. |
| رخدادها | `SystemAdminAuditEvent`, `AuditEvent` | رویدادهای مدیر و timeline موجود کسب‌وکار؛ بدنهٔ metadata خام از API فهرست رخدادها برگردانده نمی‌شود. |

یادداشت داخلی مدیر در `SystemAdminNote` نگه‌داری می‌شود و به پیام فروشنده یا timeline قابل‌مشاهدهٔ مشتری تبدیل نمی‌شود. تغییر وضعیت کسب‌وکار حذف فیزیکی ندارد؛ با دلیل و رمز فعلی تأیید می‌شود، audit دارد و دسترسی نشست فروشنده در درخواست بعدی دوباره بررسی می‌شود.

## احراز هویت، نشست و کنترل درخواست

- رمز با Argon2id و salt یکتای کتابخانه ذخیره می‌شود (پارامترهای فعلی: حافظهٔ ۱۹٬۴۵۶ KiB، دو گذر، parallelism برابر ۱). hash نشست تصادفی ۳۲ بایتی و hash CSRF در PostgreSQL نگه‌داری می‌شوند؛ مقدار خام نشست به مرورگر فقط در cookie می‌رود.
- در HTTPS نام cookie نشست `__Host-shopro_admin_session` است: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` و بدون `Domain`. در توسعهٔ محلی نام غیر `__Host` برای HTTP محلی استفاده می‌شود. cookie CSRF جداگانه خواندنی است و هر mutation مدیریتی باید همان مقدار را در `X-CSRF-Token` بفرستد.
- نشست سمت سرور پس از ۳۰ دقیقه بی‌فعالیتی منقضی و در هر حال پس از ۱۲ ساعت باطل می‌شود. مقدارها از `ADMIN_SESSION_IDLE_MINUTES` و `ADMIN_SESSION_MAX_HOURS` قابل تنظیم‌اند و بازهٔ معتبرشان به‌ترتیب ۵–۲۴۰ دقیقه و ۱–۱۶۸ ساعت است.
- ورود با Origin منطبق بر `WEB_ORIGIN` کنترل می‌شود. CORS محدود به originهای تنظیم‌شده است. Helmet، CSP پیش‌فرض، `nosniff` و cache خصوصی برای مسیرهای مدیریتی فعال‌اند.
- نرخ ورود در جدول `system_admin_login_attempts` بر مبنای fingerprint نام کاربری و IP اعمال می‌شود: پنج شکست در پنجرهٔ ۱۵ دقیقه‌ای شروع backoff افزایشی می‌دهد که حداکثر ۱۵ دقیقه است. خطای نام کاربری و رمز عمومی است. log رخداد، IP خام یا رمز را ذخیره نمی‌کند.
- تغییر رمز، همهٔ نشست‌های پیشین را باطل می‌کند و فقط یک نشست تازه می‌سازد. خروج همهٔ نشست‌ها رمز فعلی می‌خواهد. صفحهٔ نشست‌ها شناسه، زمان فعالیت و user-agent محدودشده را نشان می‌دهد؛ token را نشان نمی‌دهد.
- همهٔ controllerهای `SystemAdminOnly`، دانلود receipt و export در API به نشست مدیر نیاز دارند. `/system-admin/login` تنها صفحهٔ route مدیریتی بدون نشست است؛ بقیهٔ صفحه‌های `/system-admin` در production پیش از تحویل HTML نشست را بررسی می‌کنند. لینک پنهان در UI مجوز نیست.

### بازیابی رمز

بازیابی عمومی وجود ندارد. برای مالک فعال و یگانه، فقط اپراتوری که دسترسی console سرویس Runflare دارد می‌تواند Secretهای موقت `SHOPRO_ADMIN_RECOVERY_PASSWORD` و `SHOPRO_ADMIN_RECOVERY_CONFIRM=RESET_SINGLE_OWNER_PASSWORD` را در تنظیمات سرویس قرار دهد و `npm run admin:recover` را اجرا کند. این command حسابی نمی‌سازد، وجود دقیقاً یک مدیر را بررسی می‌کند، همهٔ نشست‌ها را باطل می‌کند و audit ثبت می‌کند. پس از اجرا هر دو متغیر باید از سرویس حذف و سرویس restart شود. رمز بازیابی در command line، shell history، log یا فایل مخزن نوشته نمی‌شود.

## API پنل

همهٔ مسیرها زیر `/api/v1` هستند. به‌جز `POST /system-admin/auth/login` که عمومی است و Origin را بررسی می‌کند، routeهای زیر نشست مالک می‌خواهند. تمام mutationها CSRF دارند.

| مسیر | کاربرد |
|---|---|
| `POST /system-admin/auth/login` | ورود با نام کاربری ثابت و رمز؛ پاسخ عمومی در خطای اعتبارسنجی حساب. |
| `POST /system-admin/auth/logout`, `PATCH /system-admin/auth/change-password` | خروج و چرخش رمز/نشست. |
| `GET /system-admin/auth/sessions`, `POST /system-admin/auth/revoke-sessions` | نشست‌های فعال و ابطال همهٔ نشست‌ها با تأیید رمز فعلی. |
| `GET /system-admin/session`, `GET /system-admin/overview`, `GET /system-admin/dashboard` | وضعیت نشست و نماهای مدیریتی. |
| `POST /system-admin/businesses/query`, `GET /system-admin/businesses/:id` | جست‌وجوی سروری، فیلتر و جزئیات کسب‌وکار با شعب، اشتراک، خلاصه سفارش/پرداخت، timeline و یادداشت داخلی. |
| `PATCH /system-admin/businesses/:id/status`, `POST /system-admin/businesses/:id/notes` | تعلیق/فعال‌سازی با دلیل و رمز فعلی؛ ثبت یادداشت داخلی. |
| `POST /system-admin/storefront-orders/query`, `POST /system-admin/search` | فهرست سفارش فروشگاه فقط‌خواندنی و جست‌وجوی دسته‌بندی‌شدهٔ اشخاص، کسب‌وکار، شعب، اشتراک و سفارش. |
| `POST /system-admin/audit/query`, `POST /system-admin/exports/:dataset` | فهرست و CSV کنترل‌شدهٔ رخدادها؛ CSV برای `businesses`, `storefront-orders`, `subscription-orders`, `audit`. |
| `/system-admin/subscriptions/*` | مدیریت پلن/قیمت، شعب و دوره، سفارش اشتراک، receipt دستی، تنظیم‌های پرداخت، rollout و گزارش اقتصادی موجود. پیش از اعطا/تمدید/توقف/رفع توقف/لغو دوره، preview سمت سرور تاریخ جلالی یا اثر وضعیت را برمی‌گرداند؛ mutation رمز فعلی، دلیل و نشست معتبر می‌خواهد و تلاش‌های تأیید مجدد rate limit می‌شوند. همهٔ endpointهای این controller نیز به نشست مالک نیاز دارند. |

جست‌وجو و جدول‌های جدید سمت سرورند؛ page size بین ۱ تا ۱۰۰ محدود است، sort از فهرست مجاز انتخاب می‌شود و tie-breaker شناسه نتیجه را پایدار می‌کند. ورودی تاریخ جلالی در رابط به مرز زمانی `Asia/Tehran` تبدیل و به API به‌شکل UTC ارسال می‌شود. مبلغ‌های ذخیره‌شده ریال و در API رشته‌اند؛ تبدیل نمایش ریال/تومان فقط در قالب‌کنندهٔ UI انجام می‌شود.

CSV دارای BOM UTF‑8 و escape سلول است تا فرمول‌های شروع‌شده با `=`, `+`, `-` یا `@` اجرا نشوند. خروجی حداکثر ۱۰٬۰۰۰ ردیف دارد. تلفن مشتری فروشگاه در CSV سفارش نیست؛ خروجی کسب‌وکار شامل نام/شناسه و شمارنده‌هاست، نه تلفن اعضا. queryهای جدید Prisma پارامتری هستند و search text در URL قرار نمی‌گیرد.

## KPI و تعریف محاسبه

بازهٔ پیش‌فرض ۳۰ روز اخیر است؛ بازهٔ مقایسه همان طول را بلافاصله پیش از بازهٔ انتخابی دارد. KPI بدون منبع معتبر با `داده در دسترس نیست` نمایش داده می‌شود.

| KPI | تعریف و منبع | محدودیت |
|---|---|---|
| کسب‌وکار فعال | شمار `Business.isActive=true` در زمان درخواست | تاریخچهٔ تغییر وضعیت در مدل کسب‌وکار نیست؛ مقدار فعلی را برای بازهٔ گذشته بازسازی نمی‌کند. |
| کسب‌وکار جدید | شمار `Business.createdAt` در بازه | timestamp ذخیره‌شده UTC است. |
| شعب فعال | شمار Branch فعال متعلق به Business فعال | وضعیت کنونی است. |
| اشتراک فعال | شمار `SubscriptionPeriod` شروع‌شده و پایان‌نیافته، revoke نشده و متصل به شعبه/کسب‌وکار فعال و بدون تعلیق | تعداد دوره است، نه تعداد مشتری یکتا. |
| شعبهٔ دارای اشتراک خریداری‌شده | شمار شعب یکتا در دوره‌های فعال با `source=PAID_ORDER` | دوره‌های اهدایی را نمی‌شمارد. |
| نزدیک پایان | دوره‌های فعال که در هفت روز آینده تمام می‌شوند | فقط بازهٔ آینده نسبت به لحظهٔ درخواست است. |
| درآمد خالص اشتراک | مبلغ `PAID` منهای `REFUNDED` با `paidAt` در بازه؛ ریال | سفارش فروشگاه عمومی را شامل نمی‌شود؛ به وضعیت فعلی سفارش متکی است. |
| سفارش اشتراک پرداخت‌شده/مستردشده | شمار `PAID` یا `REFUNDED` با `paidAt` در بازه | پرداخت ناموفق جداگانه در کارت دیگر است. |
| سفارش فروشگاه عمومی | شمار `StorefrontOrder.createdAt` در بازه | حجم سفارش است، نه درآمد وصول‌شده. |
| رسید منتظر بررسی | شمار receiptهای اشتراک `PENDING_REVIEW` در لحظهٔ درخواست | تاریخچهٔ صف نیست. |
| پرداخت ناموفق | تلاش اشتراک `FAILED` و تلاش فروشگاه `REJECTED` با `createdAt` در بازه | مطابق statusهای فعلی مدل‌ها؛ یک تعریف واحد بین دو flow نیست. |
| MRR/ARR، نرخ تمدید و نرخ ریزش | ناموجود | تمدید خودکار/cohort کامل و رخدادهای زمانی لازم در مدل حاضر وجود ندارد؛ صفر ساختگی تولید نمی‌شود. |

## Audit و دادهٔ حساس

`SystemAdminAuditEvent` در migration جدید append-only است. login موفق/ناموفق، logout، تغییر/بازیابی رمز، تأیید مجدد موفق/ناموفق، ابطال نشست، خواندن/جست‌وجو، export، تغییر وضعیت کسب‌وکار، یادداشت، تنظیمات، تغییر اشتراک و تصمیم receipt از مسیرهای مدیریتی ثبت می‌شوند. رخداد دارای زمان UTC، admin، action، entity، request ID و metadata لازم است؛ رمز، cookie، token نشست، secret، شمارهٔ کارت کامل و payload خام receipt ثبت یا در فهرست audit برگردانده نمی‌شوند. جدول و CSV فقط خلاصهٔ allowlist‌شده بر اساس action نشان می‌دهند و metadata خام به API فهرست داده نمی‌شود. درخواست فهرست audit خودش نیز ثبت می‌شود.

Receiptها از volume خصوصی موجود می‌مانند و route دانلودشان محافظت‌شده است. نقش مدیر محصول به‌صورت خودکار نقش فروشنده را دور نمی‌زند. تغییر وضعیت سفارش فروشگاه از پنل مرکزی ارائه نشده است. صفحهٔ سلامت عمومی جزئیات DB یا خطا را نشان نمی‌دهد؛ endpointهای health موجود در Runflare runbook آمده‌اند.

## Threat model و محدودیت‌ها

دارایی‌های اصلی: رمز مالک، cookie نشست، اطلاعات تماس اعضا/مشتریان، رسیدهای خصوصی، تنظیم پرداخت و رکوردهای audit. تهدیدهای اصلی: حدس رمز، سرقت/بازپخش نشست، CSRF، دسترسی مستقیم به API یا فایل، دستکاری ورودی/CSV formula injection، افشای PII در جست‌وجو و دسترسی فروشنده به پنل مرکزی. کنترل‌ها: hash رمز و نشست، timeout سمت سرور، rotation/revoke، rate limit پایدار در DB، Origin/CORS/CSRF، کنترل مجوز در server، allowlist sort/filter، page size محدود، export کمینه و masked PII.

MFA در این تغییر اضافه نشده است؛ ورود مالک بر رمز قوی، HTTPS، Secretهای سرویس و دسترسی محدود به Runflare تکیه دارد. backup خودکار Runflare، نام Project/Service و دامنهٔ واقعی از workspace قابل تأیید نبودند؛ مالک باید مقادیر و سیاست backup را در Runflare بررسی کند. این تغییر را پیش از backup پایگاه‌داده و volume رسیدها deploy نکنید.
