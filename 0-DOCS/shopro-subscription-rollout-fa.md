# راهنمای اشتراک شعبه در شاپرو

## دامنه و وضعیت پرداخت

اشتراک در نسخهٔ اول برای هر شعبه جداگانه نگهداری می‌شود. تمام مبالغ به ریال و به‌شکل رشته در API برمی‌گردند. قیمت‌های کاتالوگ اولیه برای ۱، ۳، ۶ و ۱۲ ماه به‌ترتیب ۴٬۹۷۰٬۰۰۰، ۱۳٬۷۹۰٬۰۰۰، ۲۴٬۹۰۰٬۰۰۰ و ۴۲٬۹۰۰٬۰۰۰ ریال است. دوره‌ها با تقویم جلالی و منطقهٔ زمانی `Asia/Tehran` محاسبه می‌شوند؛ لحظهٔ پایان، جزو دوره نیست.

هیچ ارائه‌دهندهٔ پرداخت برای محیط واقعی انتخاب نشده است. در `production` سفارش خرید به‌عنوان پرداخت‌نشده/در دسترس‌نبودن درگاه ثبت می‌شود و اشتراکی فعال نمی‌کند. مسیر تأیید آزمایشی فقط خارج از `production` فعال است. webhook و بازپرداخت تا زمان پیاده‌سازی و پیکربندی adapter یک درگاه واقعی با `503` رد می‌شوند. موفقیت صفحهٔ بازگشت کاربر یا دادهٔ ارسالی از مرورگر، رسید پرداخت محسوب نمی‌شود.

## Migration و کاتالوگ قیمت

پس از backup معمول پایگاه داده، migration را با دستور زیر اعمال کنید:

```powershell
npm run db:deploy
```

Migrationهای اشتراک جدول‌ها، ایندکس‌ها، قیود و رابطه‌های لازم را اضافه می‌کنند و دادهٔ کسب‌وکارها و شعب را حذف نمی‌کنند. Migration دورهٔ آزمایشی برای هر کاربر زمان اولین درخواست احراز‌شده را ثبت می‌کند و تنظیم rollout را به `ENFORCE` می‌برد؛ grace قدیمی سراسری را پاک می‌کند تا شعبه یا کسب‌وکار بعدی فرصت تازه نگیرد. Migrationهای قبلی همچنان فقط یک بار اجرا می‌شوند.

برای bootstrap مدیر تک‌مالک، راهنمای جدید [استقرار پنل مدیریت روی Runflare](../docs/RUNFLARE_ADMIN_DEPLOYMENT_FA.md) را دنبال کنید. `SHOPRO_ADMIN_INITIAL_PASSWORD` فقط به‌صورت Secret و فقط برای startup اولیه وارد می‌شود؛ seed کاتالوگ مدیر نمی‌سازد و رمز موجود را reset نمی‌کند.

برای آماده‌کردن کاتالوگ اولیه در production، پس از وجود حساب مالک، image را مستقر و فقط متغیر تأیید را موقتاً تنظیم کنید:

```text
NODE_ENV=production
SHOPRO_SUBSCRIPTION_SEED_CONFIRM=SEED_SUBSCRIPTION_CATALOG
```

بعد از اعمال متغیرها، در ترمینال سرویس Docker اجرا کنید:

```sh
npm run db:setup:production
```

این فرمان migrationهای باقی‌مانده را بررسی/اعمال می‌کند و کاتالوگ پلن `STANDARD` با چهار قیمت را به‌شکل idempotent می‌سازد. کاتالوگ فقط با دقیقاً یک حساب مالک موجود seed می‌شود؛ هیچ مدیر، کاربر، کسب‌وکار یا شعبهٔ نمونه‌ای ساخته نمی‌شود. رمز مدیر موجود تغییر نمی‌کند. Seed قیمت‌ها و تنظیم rollout موجود را بازنویسی نمی‌کند؛ فعال‌سازی `ENFORCE` و حذف grace قدیمی در migration دورهٔ آزمایشی انجام می‌شود. `npm run db:seed:subscriptions` و `npx prisma db seed` نیز در production به entrypoint کامپایل‌شدهٔ Node می‌رسند و به `tsx` که در image نهایی نصب نیست وابستگی ندارند. پس از موفقیت، متغیر تأیید را از محیط سرویس حذف کنید.

در توسعه، `npm run db:seed` همچنان دادهٔ نمونه می‌سازد و `npm run db:seed:subscriptions` فقط کاتالوگ را idempotent آماده می‌کند.

## Rollout امن

بعد از migration، `ENFORCE` فعال است. اولین درخواست احراز‌شدهٔ هر کاربر، یک مهلت ۱۴روزه ثبت می‌کند. این مهلت به نخستین کسب‌وکار او متصل می‌شود؛ اگر کسب‌وکار را بعدتر بسازد، شمارش از همان ورود شروع شده است. شعبه‌های همان کسب‌وکار از یک پایان مشترک استفاده می‌کنند و ساخت شعبه مهلت را تمدید نمی‌کند. کسب‌وکارهای بعدی کاربر دورهٔ آزمایشی ندارند. اشتراک خریداری‌شده در هر شعبه طبق دورهٔ همان شعبه اعمال می‌شود.

در طول مهلت، عملیات ثبت و ویرایش مجاز است. پس از پایان آن، فقط درخواست‌های تغییردهنده با کدهای `SUBSCRIPTION_EXPIRED` یا `SUBSCRIPTION_REQUIRED` رد می‌شوند؛ خواندن اطلاعات، گزارش‌ها و خروجی‌ها ادامه دارد و هیچ داده‌ای حذف نمی‌شود. دادهٔ صف فروش آفلاین روی دستگاه می‌ماند و پس از خرید اشتراک می‌توان آن را دستی دوباره فرستاد. تمدید اشتراک پس از انقضا نیز در دسترس می‌ماند.

پس از deploy و اجرای `npm run db:setup:production`:

1. در `/system-admin/login` با حساب مالک وارد شوید و صفحهٔ اشتراک را بررسی کنید.
2. برای کاربر تازه یا قدیمی وارد اپ شوید؛ نشان روزشمار و پیام خوش‌آمد در خانه و نوار بالای اپ ظاهر می‌شود.
3. با پایان دوره، دسترسی خواندن را در بخش‌های مختلف و ردشدن writeها را از سمت API بررسی کنید. شعبهٔ تازه در کسب‌وکار اول باید فقط روزهای باقی‌مانده را بگیرد؛ کسب‌وکار دوم باید بدون مهلت نمایش داده شود.
4. اشتراک آزمایشی پرداخت واقعی را فعال نمی‌کند؛ برای خرید production همچنان adapter معتبر درگاه یا تأیید دستی مدیر لازم است.

دوره‌های اعطایی، تمدید، تعلیق، رفع تعلیق، لغو و تغییر rollout در audit مدیر سامانه ثبت می‌شوند. حذف پلن به‌صورت غیرفعال‌کردن انجام می‌شود؛ تاریخچهٔ سفارش، تلاش پرداخت و دوره cascade-delete نمی‌شود.

## مسیرهای کاربری و مدیریتی

صفحهٔ کاربر در `/app/subscription` است و برای شعبهٔ انتخاب‌شده وضعیت، دوره، قیمت‌ها و تاریخچهٔ سفارش را نشان می‌دهد. نسخه‌ای که تاریخ امروز در پنل انتخاب قیمت دارد فوراً فعال می‌شود؛ تاریخ آینده از ساعت ۰۰:۰۰ منطقهٔ `Asia/Tehran` فعال خواهد شد. هیچ بازه‌ای به‌طور پیش‌فرض انتخاب نمی‌شود. خرید فقط برای مالک کسب‌وکار مجاز است و هر درخواست باید `Idempotency-Key` یکتا داشته باشد.

صفحهٔ مستقل مدیر سامانه در `/system-admin` است. ورود رمز و CSRF آن از نشست کاربر عادی جداست؛ OTP مدیر برداشته شده است. از بخش اشتراک می‌توان پلن و نسخهٔ قیمت را مدیریت کرد، شعب را جست‌وجو کرد، وضعیت rollout و گزارش اقتصادی را دید و با دلیل ثبت‌شده دوره اعطا/تمدید، تعلیق، رفع تعلیق یا لغو کرد. جزئیات کنترل دسترسی در [امنیت و عملیات پنل](../docs/ADMIN_PANEL_SECURITY_AND_OPERATIONS_FA.md) آمده است. اگر نسخه‌های امروز را با نسخهٔ پیشین پنل ثبت کرده‌اید و هنوز فعال نشده‌اند، روی همان ردیف «ثبت همین مبلغ از امروز» را بزنید و ثبت نسخهٔ تازه را تأیید کنید؛ نسخهٔ زمان‌بندی‌شده و تاریخچهٔ قبلی تغییر نمی‌کنند.

APIهای کاربر:

- `GET /api/v1/subscriptions/plans`
- `GET /api/v1/subscriptions/current`
- `GET /api/v1/subscriptions/orders` و `GET /api/v1/subscriptions/orders/:id`
- `POST /api/v1/subscriptions/orders` با `Idempotency-Key`
- `POST /api/v1/subscriptions/orders/:id/receipt` برای رسید خصوصی کارت‌به‌کارت
- `POST /api/v1/subscriptions/orders/:id/dev-confirm` فقط در توسعه و تست

APIهای مدیر سامانه در `/api/v1/system-admin/subscriptions` هستند: `plans`, `branches`, `orders`, `manual-payments`, `payment-settings`, `rollout`, `economics` و عملیات ثبت‌شدهٔ grant/extend/suspend/unsuspend/revoke/refund. پرداخت دستی تا تأیید رسید توسط مدیر معلق می‌ماند؛ تأیید، ثبت پرداخت، ایجاد دورهٔ اشتراک و audit را در یک تراکنش انجام می‌دهد. رد رسید با دلیل ثبت می‌شود و مالک می‌تواند رسید اصلاح‌شده بفرستد.

برای اعلان تلگرام، `TELEGRAM_BOT_TOKEN` را در Runflare به‌صورت Secret تنظیم و در پنل مدیر، مقصد را ثبت کنید. آیدی `@tiaammhd` به‌عنوان آیدی تماس نگه‌داری می‌شود؛ برای فرستادن پیام مستقیم به کاربر باید او ابتدا ربات را Start کند و chat ID عددی‌اش تنظیم شود. تنظیمات کارت و راهنما برای سفارش جدید snapshot می‌شوند و سفارش‌های قبلی اطلاعات دریافتی زمان ایجاد را نگه می‌دارند.

## پرداخت، بازپرداخت و اقتصاد

تا انتخاب درگاه واقعی، مقدار `PAYMENT_GATEWAY=fake` را در production قرار ندهید؛ حتی اگر تنظیم شود، Fake در `NODE_ENV=production` فعال نمی‌شود. برای عرضهٔ خرید واقعی باید adapter درگاه انتخابی، اعتبارسنجی امضای callback در سرور، تطبیق مبلغ/واحد، idempotency مرجع پرداخت، retry، refund واقعی و secretهای لازم اضافه و در sandbox همان درگاه آزموده شوند.

بازپرداخت فعلاً درگاه صدا نمی‌زند و اشتراک را مستردشده علامت نمی‌زند؛ تلاش مسدودشده در audit ثبت و پاسخ `PAYMENT_PROVIDER_UNCONFIGURED` برگردانده می‌شود. گزارش اقتصاد تا وقتی هزینهٔ درگاه، مالیات و هزینهٔ متغیر توسط مدیر وارد نشده باشند مقدار سود خالص را نامشخص نشان می‌دهد؛ هیچ‌کدام از این ارقام حدس زده نمی‌شوند.

## آزمون‌ها

آزمون یکپارچهٔ PostgreSQL اشتراک:

```powershell
npm run test:integration:subscriptions:local
```

پروفایل بار کامل (۲۰ VU، حداقل ۱۰٬۰۰۰ شعبه/اشتراک، پنج دقیقه):

```powershell
npm run test:perf:subscriptions:local
```

این فرمان یک PostgreSQL موقت در `.tmp` می‌سازد، migrationها را دوبار اجرا می‌کند و پس از پایان همان cluster را متوقف و پاک می‌کند. اجرای تشخیصی کوتاه فقط با `SHOPRO_SUBSCRIPTION_PERF_ALLOW_SHORT=1` ممکن است و جایگزین پروفایل پنج‌دقیقه‌ای نیست.

پروفایل محلی ۲۰ VU و پنج‌دقیقه‌ای در پایگاه آزمایشی PostgreSQL، ۷۴٬۱۹۹ درخواست را با خطای صفر اجرا کرد. p95 gate دیتابیسی ۹٫۴۱ms و اختلاف آن با baseline `SELECT 1` برابر ۰٫۷۴ms بود. p95 endpointهای کامل در همان محیط: پلن ۱۰۲٫۱۱ms، وضعیت ۱۱۳٫۷۵ms، write از HTTP تا اعتبارسنجی ۹۱٫۹۳ms و ایجاد سفارش ۱۸۲٫۵۸ms. این اعداد benchmark محیط محلی هستند، نه تضمین Runflare یا درگاه واقعی.
