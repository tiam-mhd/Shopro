# راهنمای اشتراک شعبه در شاپرو

## دامنه و وضعیت پرداخت

اشتراک در نسخهٔ اول برای هر شعبه جداگانه نگهداری می‌شود. تمام مبالغ به ریال و به‌شکل رشته در API برمی‌گردند. قیمت‌های کاتالوگ اولیه برای ۱، ۳، ۶ و ۱۲ ماه به‌ترتیب ۴٬۹۷۰٬۰۰۰، ۱۳٬۷۹۰٬۰۰۰، ۲۴٬۹۰۰٬۰۰۰ و ۴۲٬۹۰۰٬۰۰۰ ریال است. دوره‌ها با تقویم جلالی و منطقهٔ زمانی `Asia/Tehran` محاسبه می‌شوند؛ لحظهٔ پایان، جزو دوره نیست.

هیچ ارائه‌دهندهٔ پرداخت برای محیط واقعی انتخاب نشده است. در `production` سفارش خرید به‌عنوان پرداخت‌نشده/در دسترس‌نبودن درگاه ثبت می‌شود و اشتراکی فعال نمی‌کند. مسیر تأیید آزمایشی فقط خارج از `production` فعال است. webhook و بازپرداخت تا زمان پیاده‌سازی و پیکربندی adapter یک درگاه واقعی با `503` رد می‌شوند. موفقیت صفحهٔ بازگشت کاربر یا دادهٔ ارسالی از مرورگر، رسید پرداخت محسوب نمی‌شود.

## Migration و کاتالوگ قیمت

پس از backup معمول پایگاه داده، migration را با دستور زیر اعمال کنید:

```powershell
npm run db:deploy
```

Migration فقط جدول‌ها، ایندکس‌ها، قیود و رابطه‌های اشتراک را اضافه می‌کند؛ جدول‌های فعلی کسب‌وکارها و شعب را حذف یا بازنویسی نمی‌کند. اجرای migration دوباره مجاز است و در صورت نبود migration جدید تغییری اعمال نمی‌کند.

برای کاتالوگ اولیه، ابتدا حداقل یک مدیر سامانهٔ فعال داشته باشید و سپس اجرا کنید:

```powershell
npm run db:seed:subscriptions
```

این seed قیمت‌ها و پلن `STANDARD` را idempotent اضافه می‌کند و قیمت مصرف‌شده یا تنظیم مدیر را بازنویسی نمی‌کند. در توسعه، اگر مدیر فعال وجود نداشته باشد، seed مستقل یک مدیر آزمایشی می‌سازد. در محیط واقعی این رفتار وجود ندارد؛ فقط اگر اجرای seed واقعی را آگاهانه تأیید می‌کنید، متغیر زیر را برای همان اجرای کنترل‌شده تنظیم کنید:

```text
NODE_ENV=production
SHOPRO_SUBSCRIPTION_SEED_CONFIRM=SEED_SUBSCRIPTION_CATALOG
```

بعد از فرمان، متغیر تأیید را از محیط حذف کنید. seed معمول توسعه (`npm run db:seed`) نیز کاتالوگ را در همان تراکنش دادهٔ نمونه به‌شکل idempotent آماده می‌کند.

## Rollout امن

تنظیم اولیهٔ rollout `OBSERVE` است. در این وضعیت، وضعیت اشتراک محاسبه و گزارش می‌شود، اما writeهای روزمره به‌علت نداشتن اشتراک مسدود نمی‌شوند. ورود، خواندن، گزارش، خروجی و ساخت کسب‌وکار جدید از gate مستثنا هستند؛ تمدید اشتراک هم پس از انقضا در دسترس می‌ماند.

پیشنهاد اجرا:

1. migration و seed کاتالوگ را اجرا کنید.
2. در `/system-admin` با OTP مدیر سامانه وارد شوید و صفحهٔ اشتراک را بررسی کنید.
3. در `OBSERVE`، تعداد شعبه‌های بدون دورهٔ فعال را بررسی و برای هر شعبه وضعیت و تاریخ grace واقعی را مشخص کنید.
4. برای شعبی که باید فرصت انتقال داشته باشند، تاریخ پایان grace را تنظیم کنید. پیش از تغییر به `ENFORCE`، آزمون writeهای فروش، خرید، هزینه، موجودی، طرف‌حساب، کالا و تنظیمات شعبه را انجام دهید.
5. تنها پس از آماده‌شدن فهرست شعب و اطلاع‌رسانی، `ENFORCE` را فعال کنید. API فعال‌کردن آن بدون grace را، درحالی‌که شعبه‌های فعلی بدون دورهٔ فعال باقی مانده باشند، رد می‌کند.
6. با رسیدن پایان دوره، فقط writeهای عملیاتی شعبه با کدهای `SUBSCRIPTION_EXPIRED` یا `SUBSCRIPTION_REQUIRED` رد می‌شوند. دادهٔ صف آفلاین در سمت PWA حفظ می‌شود تا پس از تمدید دوباره ارسال شود.

دوره‌های اعطایی، تمدید، تعلیق، رفع تعلیق، لغو و تغییر rollout در audit مدیر سامانه ثبت می‌شوند. حذف پلن به‌صورت غیرفعال‌کردن انجام می‌شود؛ تاریخچهٔ سفارش، تلاش پرداخت و دوره cascade-delete نمی‌شود.

## مسیرهای کاربری و مدیریتی

صفحهٔ کاربر در `/app/subscription` است و برای شعبهٔ انتخاب‌شده وضعیت، دوره، قیمت‌ها و تاریخچهٔ سفارش را نشان می‌دهد. هیچ بازه‌ای به‌طور پیش‌فرض انتخاب نمی‌شود. خرید فقط برای مالک کسب‌وکار مجاز است و هر درخواست باید `Idempotency-Key` یکتا داشته باشد.

صفحهٔ مستقل مدیر سامانه در `/system-admin` است. ورود و CSRF آن از نشست کاربر عادی جداست. از بخش اشتراک می‌توان پلن و نسخهٔ قیمت را مدیریت کرد، شعب را جست‌وجو کرد، وضعیت rollout و گزارش اقتصادی را دید و با دلیل ثبت‌شده دوره اعطا/تمدید، تعلیق، رفع تعلیق یا لغو کرد.

APIهای کاربر:

- `GET /api/v1/subscriptions/plans`
- `GET /api/v1/subscriptions/current`
- `GET /api/v1/subscriptions/orders` و `GET /api/v1/subscriptions/orders/:id`
- `POST /api/v1/subscriptions/orders` با `Idempotency-Key`
- `POST /api/v1/subscriptions/orders/:id/dev-confirm` فقط در توسعه و تست

APIهای مدیر سامانه در `/api/v1/system-admin/subscriptions` هستند: `plans`, `branches`, `orders`, `rollout`, `economics` و عملیات ثبت‌شدهٔ grant/extend/suspend/unsuspend/revoke/refund.

## پرداخت، بازپرداخت و اقتصاد

تا انتخاب درگاه واقعی، مقدار `PAYMENT_GATEWAY=fake` را در production قرار ندهید؛ حتی اگر تنظیم شود، Fake در `NODE_ENV=production` فعال نمی‌شود. برای عرضهٔ خرید واقعی باید adapter درگاه انتخابی، اعتبارسنجی امضای callback در سرور، تطبیق مبلغ/واحد، idempotency مرجع پرداخت، retry، refund واقعی و secretهای لازم اضافه و در sandbox همان درگاه آزموده شوند.

بازپرداخت فعلاً درگاه صدا نمی‌زند و اشتراک را مستردشده علامت نمی‌زند؛ تلاش مسدودشده در audit ثبت و پاسخ `PAYMENT_PROVIDER_UNCONFIGURED` برگردانده می‌شود. گزارش اقتصاد تا وقتی هزینهٔ درگاه، مالیات و هزینهٔ متغیر توسط مدیر وارد نشده باشند مقدار سود خالص را نامشخص نشان می‌دهد؛ هیچ‌کدام از این ارقام حدس زده نمی‌شوند.

## آزمون‌ها

آزمون یکپارچهٔ PostgreSQL اشتراک:

```powershell
npm run test:integration:subscriptions:local
```

پروفایل بار کامل (۲۰ VU، حداقل ۱۰٬۰۰۰ شعبه/اشتراک، پنج دقیقه):

```powershell
npm run test:perf:subscriptions:local
```

این فرمان یک PostgreSQL موقت در `.tmp` می‌سازد، migrationها را دوبار اجرا می‌کند و پس از پایان همان cluster را متوقف و پاک می‌کند. اجرای تشخیصی کوتاه فقط با `SHOPRO_SUBSCRIPTION_PERF_ALLOW_SHORT=1` ممکن است و جایگزین پروفایل پنج‌دقیقه‌ای نیست.

پروفایل محلی ۲۰ VU و پنج‌دقیقه‌ای در پایگاه آزمایشی PostgreSQL، ۷۴٬۱۹۹ درخواست را با خطای صفر اجرا کرد. p95 gate دیتابیسی ۹٫۴۱ms و اختلاف آن با baseline `SELECT 1` برابر ۰٫۷۴ms بود. p95 endpointهای کامل در همان محیط: پلن ۱۰۲٫۱۱ms، وضعیت ۱۱۳٫۷۵ms، write از HTTP تا اعتبارسنجی ۹۱٫۹۳ms و ایجاد سفارش ۱۸۲٫۵۸ms. این اعداد benchmark محیط محلی هستند، نه تضمین Runflare یا درگاه واقعی.
